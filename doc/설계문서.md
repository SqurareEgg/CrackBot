## 1. 개요

### 1.1 시스템 개요

SmartCheck AI는 건축물 안전점검 현장에서 스마트폰으로 촬영한 사진을 AI가 자동 분석하여, 결함 탐지부터 공식 보고서 생성까지를 원스톱으로 처리하는 시스템이다.

### 1.2 아키텍처 패턴

| 항목 | 선택 | 이유 |
| --- | --- | --- |
| 전체 구조 | 3-tier (Client / Server / DB) | 역할 분리로 유지보수 및 스케일 아웃 용이 |
| API 방식 | RESTful (JSON) | 모바일 클라이언트와의 호환성 및 단순성 |
| AI 추론 | 별도 컨테이너 분리 | GPU 의존성 독립화, 버전 교체 유연성 확보 |
| 문서 생성 | 비동기 큐(Celery) | 처리 시간이 길어 동기 방식 적용 불가 |

---

## 2. 아키텍처 원칙

### 원칙 1. 모바일 퍼스트 (Offline-tolerant)

현장 네트워크가 불안정한 환경을 고려하여 모바일 앱은 로컬 캐시(AsyncStorage)에 촬영 데이터를 임시 저장한다. 네트워크 연결이 복구되면 자동으로 S3에 업로드하고 분석 요청을 발행한다.

### 원칙 2. AI 추론 서버 분리

YOLOv8 추론은 GPU 의존성이 높으므로 일반 API 서버와 별도 컨테이너로 분리한다. 이를 통해 AI 모델 버전 교체와 GPU 리소스 스케일 아웃이 API 서버에 영향을 주지 않도록 설계한다.

### 원칙 3. 비동기 보고서 생성

PDF/DOCX 보고서 생성은 처리 시간이 수십 초에 달할 수 있으므로 Celery 기반 비동기 작업 큐로 처리한다. API는 요청 즉시 `202 Accepted`를 반환하고, 완료 시 FCM 푸시 알림으로 앱에 통보한다.

### 원칙 4. 표준 양식 템플릿 매핑

국토안전관리원 점검 양식을 JSON 스키마로 정의하고, AI 탐지 결과를 필드 단위로 매핑한다. 양식 변경 시 스키마 파일만 수정하면 코드 변경 없이 대응 가능하도록 설계한다.

## 4. 레이어별 컴포넌트 상세

### 4.1 모바일 클라이언트 레이어

> **기술 스택**: React Native (Expo), AsyncStorage, Expo Location
> 

| 컴포넌트 | 기술 | 역할 |
| --- | --- | --- |
| 카메라 모듈 | React Native Camera | 후면 카메라 촬영, EXIF(GPS·타임스탬프) 추출, 오프라인 임시 저장 |
| GPS 위치 관리 | Expo Location | 촬영 시점 좌표 수집, 사용자 구역명과 GPS 매핑 |
| 사진 분류/관리 | AsyncStorage + S3 Multipart Upload | GPS 기반 구역별 자동 분류, 배치 업로드, 업로드 큐 관리 |
| 보고서 뷰어 | PDF Preview + FCM | 인앱 PDF 미리보기, 파일 공유, 보고서 완성 푸시 알림 수신 |

**오프라인 동작 시나리오**

1. 네트워크 없음 → 촬영 데이터 AsyncStorage 임시 저장
2. 네트워크 복구 감지 (NetInfo)
3. 업로드 큐 일괄 처리 → S3 업로드
4. 분석 요청 API 자동 발행

---

### 4.2 API 서버 레이어

> **기술 스택**: FastAPI, Uvicorn, SQLAlchemy, JWT, Python 3.11
> 

| 컴포넌트 | 기술 | 역할 |
| --- | --- | --- |
| API 게이트웨이 | FastAPI + Uvicorn | REST API 진입점, 요청 로깅, 에러 핸들링, Rate Limiting |
| 인증/인가 | JWT + OAuth2 | Access Token(15분) + Refresh Token(7일), Role 기반 권한 분리 |
| 점검 관리 서비스 | SQLAlchemy ORM | 건축물 등록, 점검 프로젝트 CRUD, 사진 업로드 수신, 탐지 작업 발행 |
| 보고서 생성 서비스 | Celery + python-docx | 비동기 보고서 생성 작업 발행, 진행 상태 관리 |

**인증 플로우**

```
클라이언트 → POST /auth/login
           ← { access_token, refresh_token }
클라이언트 → API 요청 (Authorization: Bearer <access_token>)
           ← 200 OK (토큰 유효)
           ← 401 Unauthorized → POST /auth/refresh → 새 access_token 발급
```

**역할(Role) 구분**

| 역할 | 권한 |
| --- | --- |
| `inspector` | 점검 수행, 사진 업로드, 자신의 보고서 조회 |
| `manager` | 전체 프로젝트 조회, 보고서 승인, 건축물 관리 |
| `admin` | 사용자 관리, 시스템 설정 |

### 4.3 AI 엔진 레이어

> **기술 스택**: YOLOv8, Faster R-CNN, OpenCV, PIL, Python, Celery Worker
> 

### 결함 탐지 모델 (YOLOv8 + Faster R-CNN)

| 항목 | 내용 |
| --- | --- |
| 탐지 대상 | 균열, 박락(콘크리트 탈락), 철근 노출, 백태, 누수흔적, 변형·처짐 (6대 결함) |
| 기본 모델 | YOLOv8m (실시간 탐지) |
| 정밀 모델 | Faster R-CNN (복잡한 결함 앙상블) |
| 목표 성능 | mAP@0.5 ≥ 0.90 |
| 입력 해상도 | 640×640 (YOLOv8 기본) |
| 출력 | 바운딩 박스 좌표, 결함 유형, 신뢰도(confidence) |

### 균열 폭 측정 파이프라인 (OpenCV)

```
입력 이미지
    │
    ▼
1. 전처리        — Grayscale 변환, CLAHE 히스토그램 평활화
    │
    ▼
2. 에지 검출     — Canny Edge Detection (adaptive threshold)
    │
    ▼
3. 골격화        — Skeletonization (Zhang-Suen 알고리즘)
    │
    ▼
4. 폭 계산       — 수직 방향 픽셀 수 카운트
    │
    ▼
5. 실거리 변환   — 픽셀 → mm 변환 (참조 객체 또는 카메라 캘리브레이션 활용)
    │
    ▼
출력: 균열 폭 (0.1mm 단위)
```

### 안전 등급 판정 엔진

국토안전관리원 기준을 규칙 테이블로 정의하고, ML 앙상블 결과와 가중 평균하여 최종 등급을 결정한다.

| 등급 | 기준 (주요 예시) | 조치 |
| --- | --- | --- |
| A | 결함 없음 또는 경미한 균열 (폭 < 0.1mm) | 이상 없음 |
| B | 균열 폭 0.1mm ~ 0.3mm, 소규모 박락 | 관찰 유지 |
| C | 균열 폭 0.3mm ~ 1.0mm, 철근 노출 없음 | 보수 권고 |
| D | 균열 폭 1.0mm 이상 또는 철근 노출 | 긴급 보수 |
| E | 구조 안전 위험, 붕괴 우려 | 사용 중지 + 즉시 대피 |

## 5. 주요 시나리오 데이터 흐름

### 5.1 현장 촬영 → 결함 탐지 흐름

```
[점검자 앱]                [API 서버]              [AI 워커]              [DB / S3]
    │                          │                       │                      │
    │── 촬영 + GPS 태깅 ──────▶│                       │                      │
    │── S3 Multipart Upload ──────────────────────────────────────────────▶  │
    │                          │◀── 업로드 완료 콜백 ──────────────────────── │
    │                          │── Celery Task 발행 ──▶│                      │
    │                          │                       │── S3 이미지 다운로드 ─▶│
    │                          │                       │── YOLOv8 추론 ────── │
    │                          │                       │── OpenCV 폭 측정 ─── │
    │                          │                       │── 결과 저장 ─────────▶│
    │◀── WebSocket/Polling 완료 통보 ─────────────────── │                      │
    │── 탐지 결과 화면 갱신                              │                      │
```

**단계별 설명**

1. **현장 촬영**: 점검자가 앱으로 외벽 촬영. GPS 좌표 자동 태깅, 구역별 폴더 분류.
2. **S3 업로드**: Multipart Upload로 원본 이미지 S3 저장. 오프라인 시 큐에 보관.
3. **작업 발행**: API 서버가 이미지 S3 키와 메타데이터를 Redis 큐에 Celery 작업으로 등록.
4. **YOLOv8 추론**: ai-worker가 큐에서 작업 수신 → 6대 결함 탐지 → 바운딩 박스 반환.
5. **OpenCV 측정**: 탐지된 균열 영역에 4단계 파이프라인 실행. 0.1mm 단위 수치 산출.
6. **결과 저장**: 탐지 결과(유형, 위치, 폭, 신뢰도) PostgreSQL 저장. 오버레이 이미지 S3 저장.
7. **앱 갱신**: WebSocket 또는 Polling으로 분석 완료를 앱에 전달. 결과 화면 자동 갱신.

### 5.2 보고서 자동 생성 흐름

```
[점검자 앱]             [API 서버]          [report-worker]          [S3 / FCM]
    │                      │                      │                      │
    │── POST /reports ────▶│                      │                      │
    │◀── 202 Accepted ─────│                      │                      │
    │                      │── Celery Task ──────▶│                      │
    │                      │                      │── DB 탐지 결과 조회  │
    │                      │                      │── 양식 스키마 매핑   │
    │                      │                      │── DOCX / PDF 생성    │
    │                      │                      │── S3 업로드 ─────────▶│
    │◀── FCM 푸시 알림 ─────────────────────────────────────────────────  │
    │── 보고서 다운로드 / 공유                     │                      │
```

**단계별 설명**

1. **요청**: 앱에서 "보고서 생성" 버튼 클릭 → `POST /reports/{inspection_id}`.
2. **즉시 응답**: API 서버는 `202 Accepted` 반환 (비동기 처리).
3. **스키마 매핑**: 국토안전관리원 JSON 스키마 필드에 탐지 결과 데이터 매핑.
4. **문서 생성**: python-docx(DOCX), ReportLab(PDF) 렌더링. 오버레이 이미지 임베드.
5. **배포**: 생성 파일 S3 업로드, Pre-signed URL 생성. FCM 푸시 알림 발송.
6. **확인**: 점검자가 앱 내 뷰어로 즉시 확인하거나 이메일·메신저로 공유.

---

### 5.3 안전 등급 판정 흐름

1. **집계**: 건축물의 전체 탐지 결과(결함 유형, 개수, 최대 균열 폭, 철근 노출 여부)를 DB에서 집계.
2. **규칙 기반 1차 판정**: 국토안전관리원 기준 규칙 테이블 적용 → A~E 등급 1차 산정.
3. **ML 앙상블 2차 판정**: 탐지 결과 벡터를 경량 분류 모델(XGBoost)에 입력 → 2차 등급 예측.
4. **최종 등급 결정**: 1차(규칙 기반) 70% + 2차(ML) 30% 가중 평균 → 최종 등급 결정. 근거 조항 및 권고사항 텍스트 자동 생성.
5. **이력 저장**: 등급 판정 결과와 근거 데이터를 시계열로 기록. 이전 점검 이력과 비교하여 결함 진행 속도 계산.

| 주요 버튼 | 촬영 계속 → SCR-06 / 보고서 생성 → SCR-14 |
| 구역 탭 | 해당 구역의 사진 목록 및 결함 상세 확인 |

---

### SCR-13 프로젝트 생성

| 필드 | 필수 여부 | 비고 |
| --- | --- | --- |
| 건물명 | 필수 | 최대 50자 |
| 주소 | 필수 | 주소 검색 API 연동 |
| 시작일 | 필수 | 날짜 피커 |
| 종료 예정일 | 선택 | 시작일 이후만 선택 가능 |
| 점검 구역 | 선택 | 최대 10개, 자유 명칭 |
| 담당 점검사 | 선택 | 팀 내 사용자 목록에서 선택 |
- 생성 완료 후 → SCR-12 프로젝트 상세로 이동
- 필수 필드 미입력 시 버튼 비활성화

| INSPECTION_PROJECTS → INSPECTION_ZONES | 1 : N | 프로젝트 1개에 여러 점검 구역 포함 |
| INSPECTION_PROJECTS → SAFETY_GRADES | 1 : N | 프로젝트 전체 + 구역별 등급 이력 관리 |
| INSPECTION_PROJECTS → REPORTS | 1 : N | 프로젝트 1개에 여러 보고서 생성 가능 |
| INSPECTION_ZONES → INSPECTION_PHOTOS | 1 : N | 구역 1개에 여러 촬영 사진 포함 |
| INSPECTION_ZONES → SAFETY_GRADES | 1 : N | 구역별 등급 이력 (시계열 관리) |
| INSPECTION_PHOTOS → DEFECT_DETECTIONS | 1 : N | 사진 1장에서 여러 결함 탐지 가능 |

**페이지네이션 응답**

```json
{
  "success": true,
```

## 2. DB 스키마 변경

### 신규 테이블: PROJECT_MEMBERS

```sql
CREATE TABLE project_members (
  id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  project_id  UUID NOT NULL REFERENCES inspection_projects(id) ON DELETE CASCADE,
  user_id     UUID REFERENCES users(id),           -- 사람 팀원 (NULL이면 로봇)
  device_id   UUID REFERENCES robot_devices(id),   -- 로봇 (NULL이면 사람)
  role        project_member_role NOT NULL,         -- leader / member / viewer / robot
  status      member_status NOT NULL DEFAULT 'pending', -- pending / active / removed
  invited_by  UUID NOT NULL REFERENCES users(id),
  joined_at   TIMESTAMP,
  created_at  TIMESTAMP NOT NULL DEFAULT NOW(),
  CONSTRAINT chk_member_type CHECK (
    (user_id IS NOT NULL AND device_id IS NULL) OR
    (user_id IS NULL AND device_id IS NOT NULL)
  )
);
```

### 신규 테이블: ROBOT_DEVICES

```sql
CREATE TABLE robot_devices (
  id           UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  device_name  VARCHAR(100) NOT NULL,
  device_token VARCHAR(512) NOT NULL UNIQUE,  -- API 인증용 토큰
  owner_id     UUID NOT NULL REFERENCES users(id),
  is_active    BOOLEAN NOT NULL DEFAULT TRUE,
  last_seen_at TIMESTAMP,
  created_at   TIMESTAMP NOT NULL DEFAULT NOW()
);
```

### 기존 테이블 컬럼 추가

**USERS**

```sql
ALTER TABLE users ADD COLUMN company_name VARCHAR(100);
```

**INSPECTION_PROJECTS**

```sql
ALTER TABLE inspection_projects
  ADD COLUMN description      TEXT,
  ADD COLUMN blueprint_s3_key VARCHAR(500),
  ADD COLUMN basement_floors  INTEGER CHECK (basement_floors >= 0),
  ADD COLUMN above_floors     INTEGER CHECK (above_floors >= 1),
  ADD COLUMN has_roof_floor   BOOLEAN NOT NULL DEFAULT FALSE,
  ADD COLUMN has_penthouse    BOOLEAN NOT NULL DEFAULT FALSE,
  ADD COLUMN has_rooftop      BOOLEAN NOT NULL DEFAULT FALSE;
```

**REPORTS**

```sql
ALTER TABLE reports
  ADD COLUMN company_name VARCHAR(200),
  ADD COLUMN summary      TEXT;
```

### 신규 ENUM 타입

```sql

CREATE TYPE member_status AS ENUM ('pending', 'active', 'removed');
```


## 4. 자율주행 로봇 연동 아키텍처

### 연동 흐름

```
1. 디바이스 등록
   관리자 앱 → POST /devices → device_token 발급
   SCR-18에서 프로젝트 팀원으로 등록 (role: robot)

2. 현장 투입
   로봇 → POST /robot/photos/upload-url (DeviceToken 인증)
        → S3 Pre-signed URL 수신

3. 이미지 전송
   로봇 → S3에 직접 PUT 업로드
   로봇 → POST /robot/photos/{id}/analyze

4. AI 분석 (기존 파이프라인)
   Celery ai-worker → YOLOv8 탐지 → OpenCV 폭 측정 → 등급 판정
   WebSocket/FCM → 앱 팀원 전원에게 결과 푸시

5. 팀원 앱 확인
   SCR-07에서 로봇 업로드 이미지 + 탐지 결과 실시간 확인
```

### 인증 방식 비교

| 주체 | 인증 방식 | 토큰 유효기간 |
| --- | --- | --- |
| 사람 (앱 사용자) | `Authorization: Bearer <JWT>` | Access 15분 / Refresh 7일 |
| 자율주행 로봇 | `Authorization: DeviceToken <token>` | 무기한 (수동 폐기) |

### 로봇 권한 검증 로직

```
1. Authorization 헤더에서 DeviceToken 추출
2. ROBOT_DEVICES 테이블에서 device_token 조회 → device_id 확인
3. PROJECT_MEMBERS에서 device_id + zone 소속 프로젝트 확인
4. is_active = true AND status = 'active' 확인
5. 검증 통과 시 업로드 허용
```
